# Workflow import and operation

Pinned target: n8n **2.43.6**. Exports contain only official Webhook, Schedule Trigger, Manual Trigger, HTTP Request, Code, IF, Postgres and AWS SES nodes. `scripts/validate_workflows.py` checks JSON structure/connections; it cannot establish runtime compatibility by itself.

After `docker compose up -d --build`, run with the local Python environment and PYTHONPATH=backend:

```powershell
.\.venv\Scripts\python scripts/import_n8n.py
```

The script imports a local header credential over stdin into a short-lived container file with mode 0600, deletes it after import, imports all three exports, publishes A, B and C, and restarts n8n. The credential is `Loan internal header` (ID `loan-internal-header`), type Header Auth, header name `X-Workflow-Secret`, value from `.env`. No decrypted credential export is committed. If CLI publication differs in your installed version, use the editor Publish control for B/C and restart the dispatcher only after both webhooks are registered.

Manual UI import: select each JSON under `n8n/workflows/`, configure that same Header Auth credential on webhook/HTTP nodes, and publish A/B/C. Workflow IDs are `loan-workflow-a`, `loan-workflow-b`, `loan-workflow-c` when using the supplied CLI import. Paths: `POST /webhook/loan-b`, `POST /webhook/loan-c`. Requests without the configured header must be rejected. The webhook returns acceptance immediately; inspect service audit rows and n8n execution metadata for actual completion.

A's schedule is daily at 09:00 Asia/Kolkata, but A is published with all live sources disabled. Three source candidates fail closed at the permission gate and produce crawler audit rows. Its manual branch and authenticated `/webhook/loan-a-demo` branch fetch three bundled fictional HTML pages through HTTP, then normalize, extract, validate and upsert them. The dashboard discovery button invokes that webhook through the authenticated API. Fixture extraction accepts only the bundled HTML and requires DEMO_MODE. Review robots, page accessibility and published usage restrictions, record evidence/date, add source-specific extraction tests, and update both `n8n/sources.json` and generated exports before enabling any live source. Run `python scripts/generate_workflows.py` after source configuration edits. A source extraction is not lender verification; live products remain UNVERIFIED.

B checks UUID-shaped job ID and completed metadata, runs parameterized SQL in its Postgres node, evaluates advanced rules using n8n/advanced_rules.js, and submits outcomes for backend revalidation and bulk persistence. A dedicated read-only PostgreSQL credential is created by the import script; manually configure ID loan-domain-postgres for UI imports. Filtered candidates are pseudonymous and read in ordered 1,000-row keyset pages. Each page is revalidated and committed with a job-locked durable cursor and criteria fingerprint. PARTITIONING pages cannot release notifications; a short or empty final page records PERSISTED; its final acknowledgement node marks B COMPLETED and creates C's outbox event; it never claims success simply from HTTP acceptance. C verifies B completion, selects grouped unnotified users, and calls the allowlisted delivery service in batches of 100. Repeated webhook deliveries are idempotent; pending batches are drained by dispatcher retries. Original email addresses never enter n8n execution data.

Credentials and workflow publication are persistent in PostgreSQL/n8n volumes. Encryption key must be preserved between restarts. Execution payloads contain pseudonymous IDs and product criteria, never user email addresses or names, and are pruned after 24 hours. Successful payloads are retained to support execution evidence and avoid observed stale running metadata when success storage was disabled. A related upstream report is https://github.com/n8n-io/n8n/issues/38551; that report does not establish the exact cause of this instance's behavior. The local stack is loopback-only and uses HTTP; production requires private connectivity and TLS. The SQL node needs the read-only PostgreSQL credential. Default Mailpit delivery stays in the authenticated notification service. The separately gated SES-node path requires its own least-privilege n8n AWS credential. Set DEMO_MODE=true only for local fixture matching; production must use false.

The domain reader receives SELECT only on users.id, job_id, monthly_income, credit_score, employment_status and age, plus product/criteria tables. Names and contact email are denied at column privilege level. [Runtime verification](../reports/runtime-verification.json) records the observed role privileges and a denied email/name query.

The n8n container does not need WORKFLOW_SECRET in its environment: webhook and HTTP nodes use the imported encrypted header credential. The application still loads the same secret from its environment, and the importer configures the credential from local settings. DEMO_MODE remains available to the candidate SQL expression.


## Updating the API and workflows together

The updated B/C exports require the new private progress/page and reservation/receipt endpoints. Rebuild/start the API and worker image before importing the exports in an approved maintenance window. Do not deploy the new exports against the old running image. The standard importer above rotates the domain-reader password; an existing installation can instead import/publish only the workflow definitions with its existing credentials, as in the approved [controlled integration run](../reports/integration-verification.md). That run installed the new graphs and executed A with fixtures and B/C with three synthetic 12-row jobs. It preserved credentials, historical records and the original Mailpit captures. Historical import/execution reports describe older graphs; the new integration report records current installed versions and execution IDs.

The controlled run retained a separate Mailpit inbox on localhost:18025 and a private Compose SMTP safety override. Preserve that override for subsequent service recreation; ordinary Compose defaults route to the original inbox, which was already at its retention limit. The temporary five-candidate page setting was removed and the API default is again 1,000. No further uploads or sends are authorized by the report.

## Optional SES node - CONFIGURED, real delivery UNVERIFIED

For the disabled, uninstalled single-recipient test draft, Console instructions and pre-send/rollback checklist, see [SES phase 1 preparation](ses-test/README.md). It requires separate credential-installation and send approvals and does not change the verified Mailpit workflow.

1. Obtain explicit approval for a real test. In the selected AWS region, verify the sender and the controlled recipient (or its verified domain); SES sandbox restrictions apply. Configure the exact controlled inbox/plus alias. Never derive an address from CSV data.
2. Create an n8n AWS credential named `Loan SES controlled test` (export reference ID `loan-ses-test`). Select its SES region and supply credentials through the editor/credential store or an approved workload identity. Scope `ses:SendEmail` to the sender identity and restrict SES recipients to that inbox. No decrypted credentials are exported or created by the local importer.
3. On the private API set `N8N_SES_ENABLED=true`, `EMAIL_DELIVERY_MODE=test`, `SES_SENDER` and `NOTIFICATION_TEST_INBOX`. The current `.env` was not changed; `.env.example` defaults to preview and disabled integrations. Granting the API flag alone does not enable the exported SES node.
4. Explicitly enable `AWS SES controlled test` in C and select the credential. Keep Retry On Fail disabled. The backend first claims one PENDING event, stores SENDING plus execution ownership, then returns only synthetic greeting/product content and the allowlisted destination. C calls the SES node once, parses `SendEmailResponse.SendEmailResult.MessageId`, and posts an authenticated receipt. The successful callback marks SENT; errors or missing acknowledgements mark UNKNOWN. Lost claim/receipt responses leave SENDING for reconciliation. A deliberately disabled node cannot create a false SENT receipt.
5. Test only a small approved synthetic job. Inspect notification rows and actual inbox receipt. A provider MessageId is not inbox-delivery evidence. Do not rerun a selected SES node, reset an uncertain event, or replay old Mailpit events to manufacture SES evidence. Exactly-once provider delivery is not promised. Existing SENT events are never resent by this path.

The gated path handles one reserved user per C execution; dispatcher retries drain pending events while recording progress. This is intentionally conservative for controlled tests, not a throughput benchmark. Native SES Send sends HTML; default Mailpit and the service SDK retain both HTML/plain text. The SDK uses one total attempt; native-node retries are disabled. Preview mode retains the original 100-user service batch path.
